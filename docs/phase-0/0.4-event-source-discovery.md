# Phase 0.4 — Event Source Discovery

## Purpose

Determine whether Raleigh/Wake plus the seven Census-adjacent counties have enough discoverable, maintainable event data to justify building ingestion in Phase 0.5.

This checkpoint audits **coverage, authority, structure, maintenance risk, access requirements, and adapter reuse**. It does not yet claim complete event ingestion.

## POC market

Home: Wake County (`37183`)

Adjacent: Chatham (`37037`), Durham (`37063`), Franklin (`37069`), Granville (`37077`), Harnett (`37085`), Johnston (`37101`), Nash (`37127`).

## Key findings

1. No single source is sufficient.
2. Official county calendars vary dramatically in event usefulness.
3. Tourism calendars are essential for festivals, food, music, attractions and visitor-facing happenings.
4. University calendars materially improve Raleigh/Durham coverage.
5. CivicEngage is a high-leverage adapter family because multiple counties expose iCalendar from the same platform pattern.
6. Simpleview-style tourism calendars appear across multiple destination sites and should be investigated as another reusable adapter family.
7. Commercial APIs improve major-event recall but cannot replace local calendars.
8. Community aggregators are useful for small-event discovery but should not outrank first-party evidence.
9. Eventbrite must not be assumed to provide a supported public geographic discovery API: its Event Search API was retired.
10. Nash County is the weakest county in the current official-calendar set and needs supplemental discovery sources.

## Phase 0.5 initial ingestion set

The registry enables a deliberately mixed set:

- City of Raleigh Events
- Visit Raleigh Events
- NC State University Calendar
- City of Durham Calendar
- Chatham County Calendar
- Franklin County Calendar
- Granville County Calendar
- Johnston County Visitors Bureau Events
- Ticketmaster Discovery API (when API credentials are supplied)

This exercises custom municipal HTML, tourism/Simpleview, Localist/feed, CivicEngage/iCalendar and commercial API adapters.

## Readiness model

`ready`: public ingestion path is clear enough for Phase 0.5.

`requires_key`: technically ready but needs an API credential.

`candidate`: useful source, but endpoint/feed/parser work should be resolved before enabling.

`licensed`: suitable only if a paid/subscription access decision is made.

`deferred`: deliberately excluded from broad discovery for this POC.

## Source scoring

Scores are 1–5 for:

- authority (derived from tier; Tier 1 is strongest)
- structure
- coverage
- maintenance
- cost/access

The combined score helps prioritize engineering work; it does not override source authority in factual conflicts.

## Coverage risk

**Wake and Durham:** strong, due to municipal + tourism + university + commercial layers.

**Johnston:** strong-to-moderate, with a broad visitors-bureau calendar and RSS.

**Chatham / Franklin / Granville:** moderate-to-strong; county calendars include meaningful community/library/recreation activity.

**Harnett:** moderate; official upcoming events exist, but a durable dedicated feed still needs discovery.

**Nash:** weak-to-moderate; official calendar structure is good but observed event breadth is low. Rocky Mount and broader aggregators should supplement it.

## Phase 0.5 handoff

Implement source adapters by reusable family, fetch a bounded future date window, normalize raw events into the Phase 0.1 Event contract, preserve raw provenance, and measure:

- raw items per source
- usable event percentage
- missing location/time fields
- duplicate rate
- per-county/category coverage
- parser failures and source drift
- fetch latency and source health
