# Phase 0.5 — Event Ingestion POC

## Purpose

Prove that heterogeneous event sources can be loaded from a dynamic catalog, parsed through reusable adapter families, normalized into one source-backed event candidate model, measured independently, and changed without shipping a new client.

## Dynamic source repository

The Phase 0.4 source registry remains the discovery inventory. Phase 0.5 adds a server-managed overlay that can change endpoint, adapter family, enabled state, lifecycle, non-secret adapter configuration and a server-side secret reference.

Effective catalog layers:

1. built-in/curated discovery registry;
2. server-managed overlay;
3. approved user-source records.

Server entries may update curated sources. User entries receive a `user:` namespace and cannot replace curated source IDs. Catalog revisions use a deterministic hash so ingestion results can record exactly which source configuration produced them.

## User-added sources

Initial self-service support is deliberately bounded to RSS, Atom and iCalendar over public HTTPS. A proposed source starts disabled at authority Tier 4 with `proposed` trust state, must pass URL/network validation, cannot include inline credentials, and must be approved before ingestion.

Custom HTML parsing, commercial APIs and other high-maintenance adapters remain server-curated. This can expand later after source reputation and validation workflows exist.

## Adapter families implemented

- iCalendar / CivicEngage-style feeds;
- RSS / Atom-style event feeds for tourism/community feeds;
- Localist JSON API;
- Ticketmaster Discovery API response normalization;
- curated structured-HTML card parsing for server-authored adapters.

The Localist adapter follows Localist API v2 event/instance structure. Ticketmaster follows Discovery API v2 event/venue/classification structure.

## Event candidate contract

Phase 0.5 intentionally emits `candidate1:` IDs rather than pretending cross-source duplicates are solved. Each candidate preserves source ID, provider external ID, title, start/end, location fields, category hints, status, source URL, retrieval time and a SHA-256 hash of retained raw evidence.

## Source metrics and failure isolation

Every source produces independent metrics for fetched, accepted and rejected items, missing title/start/location fields, and parser/fetch errors. One source failure does not stop other sources from producing candidates.

## POC source configuration

`poc/sources/data/phase_0_5_overlay.json` is the first server-managed source overlay. It includes configuration for NC State Localist, Durham/Franklin/Granville CivicEngage discovery, Visit Raleigh and Johnston tourism feeds, Raleigh curated HTML, and Ticketmaster as a credentialed source that remains disabled until a key is supplied.

The build environment does not have direct outbound Internet access, so live transport execution is not claimed here. Current source capabilities were independently verified during discovery, while deterministic tests exercise the parser and catalog contracts.

## Deferred-source repository

Deferred and future sources remain data instead of being discarded. The Phase 0.4 registry retains 19 discovered candidates, and `poc/sources/data/backlog/` adds expandable category-specific candidate inventories. This lets us retain municipal, county, library, university, tourism, venue, community and future user-submitted sources without enabling them prematurely.

## Validation

The Phase 0.5 build workspace passed 21/21 new catalog/adapter/normalization/service tests plus Python compile validation. The GitHub connector accepted the runtime implementation and catalog tests; some source-shaped fixture/test payloads are validated in the build workspace rather than claimed as remotely executable fixtures.

## Phase 0.5 exit criteria

- catalog is dynamically overlayable;
- user-added standard feeds have a bounded proposal/approval path;
- outbound URL/credential safety controls exist;
- at least four heterogeneous adapter families normalize into one model;
- raw evidence hashes and provenance survive normalization;
- missing-field/source-health metrics are measurable;
- source failure is isolated;
- deferred sources remain represented in a maintained backlog;
- deduplication is explicitly deferred to Phase 0.6.

## Phase 0.6 handoff

Use candidate sets to implement entity resolution and taxonomy enrichment. Preserve all source provenance while measuring exact/near duplicate rates, recurrence behavior, conflicting times/locations, authority preferences and cross-source merge confidence.
